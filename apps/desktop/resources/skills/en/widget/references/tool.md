# The `widget` tool's building actions

Every agent with the `widget` tool can `list`, `describe` and `call`; you also have the building actions below because you hold this skill. Ids are lowercase ASCII kebab-case with at least one dash; anything else is refused.

| Action    | Parameters                                     | What it does                                                                                                                                                                                                                       |
| --------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list`    |                                                | Every widget: id, name, description, its folder, its operations (name, read / write, first sentence) and what this conversation may do with it (`none` / `read` / `read-write`). An older widget shows `storage="legacy-postgres"`; one that moved to SQLite but still keeps its old data shows `old-data="legacy-postgres"` (`sql` with `legacy: true` reads it). |
| `describe`| `widget`                                       | Each operation's full description and its input and output JSON Schemas.                                                                                                                                                          |
| `create`  | `widget` (the new id), `name`, `description`   | Scaffold a new widget and run its first build. Returns its folder, its files and the build's outcome.                                                                                                                             |
| `build`   | `widget`, `message`                            | Build the screen and the API. Returns the errors, or the operations now live, warnings, and the commit. A failed build changes nothing that is running.                                                                          |
| `call`    | `widget`, `op`, `args`, `dry_run`              | Run one operation, exactly as the screen would. With `dry_run: true` everything it wrote is rolled back afterwards, and screen-only operations can be called too.                                                                  |
| `preview` | `widget`, `sizes`, `theme`                     | Screenshots of the screen at `panel`, `window` and `phone` (default all three), `light` or `dark` (default the app's), as images in the result, plus the errors the page logged. Nothing opens on screen.                          |
| `sql`     | `widget`, `sql`, `legacy`                      | Run SQL on the widget's database: create and change tables, look at rows, fix data. A script of several statements runs in one transaction. `legacy: true` runs it on an older widget's data in the shared PostgreSQL database.     |
| `export`  | `widget`, `path`                               | Package a standalone Vite project into one .zip (`export.md`).                                                                                                                                                                     |
| `open`    | `widget`                                       | Open it in its own window on the computer running ShuviX. Only when the user asks you to.                                                                                                                                          |

## Details that matter

- **Permission**: using a widget needs the user's permission for this conversation, read (calling read operations, `preview`, `export`) or read-write (calling operations that write, `build`, `sql`), and the user answers it on a card the first time. A widget you `create` is read-write for this conversation already. Read-write also lets you edit its folder; without it, writes there ask. If the user declines, do not look for another way in.
- **A failed build** is a normal, recoverable outcome: fix what it reports and build again.
- **Commits**: after a green build ShuviX commits the whole widget folder, deletions included. `message` is that commit's subject (default `chore(<id>): build`); write what changed, in one line. You never run git, and you never touch `.git`.
- **Only a built API is live**: editing `api.ts` changes nothing until `build` succeeds, so a screen and an API always change together.
- **`sql`** passes a lexical check: `ATTACH`, `DETACH`, `VACUUM`, `PRAGMA` and `load_extension` are refused (`data.md`). Do not write `BEGIN` / `COMMIT` in a script; the whole script already is one transaction.
- **`open`** shows the window on the computer where ShuviX runs. When the user is on ShuviX's web page, or ShuviX runs headless (where `open` fails), tell them to open the widget from the Widget panel instead; it opens in a new browser tab there.
- **The shell**: there is no `shuvix widget` command any more, and a widget's routes refuse requests from your shell. Test operations with `call`, look at data with `sql`, look at the screen with `preview`.
