# ナレッジベースのエントリ

**ナレッジベース**は markdown のディレクトリ、**エントリ**はその中の一つの `.md` です。ShuviX は
Open Knowledge Format（OKF）v0.2 に、小さな独自プロファイルを添えて従います：frontmatter は
メタデータ、本文は知識、予約名は `index.md` と `log.md` だけです。

## ベースの場所

| ベース              | ディレクトリ                                                                              | `knowledge` ツールでの名前   |
| ------------------- | ----------------------------------------------------------------------------------------- | ---------------------------- |
| ユーザー自身の      | `~/.shuvix/knowledge/<name>/` —— **隠しでないサブディレクトリはすべて一つのベース**。マーカーファイル不要 | ディレクトリ名        |
| このプロジェクトの  | `~/.shuvix/knowledge-shuvix/projects/<projectId>/`（ツール経由で書かれ、手では書かない）    | `project`（予約名）          |
| ShuviX のリファレンス | アプリケーション内（読み取り専用、UI 言語ごと）                                          | `shuvix`（予約名）           |

ベースに必要なのはディレクトリだけです：ノートのフォルダをコピーして入れれば、それがベースです。
隠しファイルとディレクトリ（`.obsidian/`、`.trash/`、`.git/`）は決してベースの一部になりません。
各ベースは独自の git 履歴を持ちます：ShuviX が観測した最初の書き込みで（フォルダにリポジトリが
無ければ）`git init` し、その時点のフォルダをベースラインとし、以後観測されるすべての変更を
`kb(<op>): /path` として `Knowledge-Op` / `Knowledge-Actor` トレーラー付きでコミットします。

**プロジェクト内のセッションには、そのプロジェクトのベース `project` が常に付き、先頭に並びます** ——
プロジェクトについて分かったことはそこに記録するので、チェックするものではありません（設定カードにも
出ません）。**それ以外のベースはユーザーの選択です**（セッション設定 → ナレッジベース；プロジェクト
設定は新しいセッションの既定を決める）。未設定なら親セッション、次にプロジェクトの既定に従い、誰も
選んでいなければ**ほかのベースは一つも有効になりません** —— `shuvix` も例外ではありません。選択は固い境界です：
`bases` は有効なものだけを一覧し、それ以外の名前を名指すと拒否されます。システムプロンプトの
`<knowledge_bases>` フェンスも同じ名前を一覧します。

選択は、エージェントが確認なしに触れられる範囲も決めます。有効なベースはセッション自身の**読み書き
できる**ディレクトリです（`policy-md` エントリの `vars.sessionDirs`）：そこでのファイルの読み取り・作成・
編集は確認なし —— ファイルツールでもサンドボックス内のコマンドでも同じ —— です。ベースの変更はすべて
そのベース自身の git にコミットされ、元に戻せるからです。`shuvix` は有効なとき**読み取り専用**の
セッションディレクトリで、読むのは確認なし、書くのは確認ありです。有効でないベースはホームフォルダの
他のフォルダと同じで、読むときに確認が出ます。

## 広く読み、厳しく書く

- ベース内の隠しでない**すべての** `.md` は**ノート**です：サイドバーに並び、検索され、読めます ——
  タイトルは frontmatter の `title` → 最初の `# 見出し` → ファイル名。メタデータは不要で、ShuviX が
  ユーザーのノートを書き換えてメタデータを足すことはありません。
- ノートは、frontmatter がマッピングとして解析でき、空でない文字列の `type` を持ち、*他所の*
  `shuvix:` マーカーを持たないとき、加えて **OKF エントリ（概念）**でもあります（ベース内の
  `shuvix: agent v1` ファイルはノートであって概念ではない）。`knowledge` ツールの `submit` を
  通ったエントリだけが、準拠を**確認**されています。
- `index.md` と `log.md` は OKF の予約名です。ShuviX はもう生成しません。以前に生成したものは
  形で隠され、手書きの同名ファイルは普通のノートです（決して概念ではない）。

## frontmatter キー（ShuviX プロファイル）

ふつうの順に：

| キー            | 型                                                           | 必須                    | 意味                                                                                                                                                                                                                                       |
| --------------- | ------------------------------------------------------------ | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `shuvix`        | `okf v0.2`                                                   | いいえ                  | 自己申告：「これは OKF v0.2 で書かれた OKF エントリ」。ノートブックのプロパティカードはこれで選ばれる。無いノートも解析される。他の `shuvix:` 種別は「概念ではない」を意味する。                                                          |
| `type`          | 文字列                                                       | **はい**（概念には必須） | どんな種類のものか。ShuviX の開かれた語彙：`Memory`、`Concept`、`Entity`、`Decision`、`Guide`、`Source` —— 他の値も許され、そのまま表示される。                                                                                            |
| `title`         | 文字列                                                       | いいえ                  | 表示タイトル。既定：`.md` を除いたファイル名。                                                                                                                                                                                             |
| `description`   | 文字列                                                       | いいえ                  | **このエントリを開く価値があるのはいつかを述べる一行** —— `list` と `search` が表示するもので、後のセッションが読むかどうかを決める材料。                                                                                                     |
| `resource`      | 文字列                                                       | いいえ                  | エントリが表す外部ロケーター（まれ）。                                                                                                                                                                                                     |
| `tags`          | 文字列のリスト（カンマ区切り文字列も読める）                 | いいえ                  | 自由なタグ。                                                                                                                                                                                                                               |
| `status`        | `draft` \| `stable` \| `deprecated`                          | いいえ                  | **ライフサイクル**、既定 `stable`：`draft` = まだ不完全、`stable` = 頼れる、`deprecated` = リンクと履歴のために残す（検索から外れる）。提出時に明示的に書き出される。レビューのフラグでは**ない**。                                              |
| `stale_after`   | `YYYY-MM-DD`                                                 | いいえ                  | この日を過ぎるとエントリは再確認が必要（サイドバーにバッジ）。                                                                                                                                                                             |
| `sources`       | `{ id?, resource, title?, author?, last_modified? }` のリスト（素のロケーター文字列も可） | いいえ | 主張の出所。`resource` は自己完結したロケーター：絶対パス（`#symbol` 付き可）、完全な URL、`<remote-url>@<commit>:<path>`、または `shuvix://session/<id>`。`id` は脚注引用 `[^id]` を可能にする。                                        |
| `generated`     | `{ by, at }`                                                 | いいえ                  | **ホストのスタンプ** —— 内容を書いたのは誰か（`shuvix-<agent>/<model>`）、いつか（ISO 8601）。エージェントがエントリを編集するたびに書き込みフックが更新し、エントリが `submit` に合格すると提出したエージェントに書き換わる。手で設定しないこと。サイドバーの「新規エントリ」は意図的に省く。 |
| `verified`      | `{ by, at }` またはそのリスト                                | いいえ                  | **レビュー軸**：誰がエントリを確認したか。人による確認（`by: human:…`）は UI 操作だけが書く。`submit` に合格するとナレッジライターの機械確認（`by: shuvix-knowledge-writer/<model>`、以前のものを置き換える）が加わる。**エージェントは決して書かない。** ここから信頼段階 —— 機械確認か人手レビューか、`generated.at` より古くない確認だけを数える —— と「確認後に編集あり」バッジ（すべての確認が `generated.at` より古い）が導かれる。 |

未知のキーはそのまま保持されます。形が違う値は警告として報告され既定値に落ちます。frontmatter が
無いか、`type` が欠落・空のときだけ、ファイルは「概念ではない」ものになります。

## 本文

Markdown。**同じベース**内の他のエントリへは、バンドル絶対の markdown リンク ——
`[Agent 定義ファイル](/agent-md.md)`、ルートはベースのディレクトリ —— で。検証はベース内で解決
できないリンクに警告します。**別のベース**やセッションを指すには、パスではなく `shuvix://` URI を
使います（リンク検査はスキームを持つものを飛ばす）。見出し、コードフェンス、脚注は普通の markdown。
先頭の `# 見出し` は、frontmatter のないノートのタイトルを兼ねます。

## ファイル名

エントリのファイル名は書く人が付け、その名前がエントリの恒久的な id になります —— 主題にちなんで
名付けてください。ベース内では、`write` はエージェントが読んでいない既存ファイルの上書きを拒否するので、
使用済みの名前を選んでも他人のエントリが黙って置き換わることはありません。サイドバーの**新規エントリ**は
タイトルからファイル名を導きます：あらゆる文字体系の文字と数字は保持、それ以外の連続は `-` に、ASCII は
小文字化、60 文字で切り詰め、使用済みの名前には `-2`、`-3`、…（予約名も使用済み扱い）。

## エントリの書き方と変え方

- **`write` でベースのディレクトリに書きます**。普通の markdown で —— 一つの主題に一つのファイル、
  frontmatter は不要、各主張の出典を本文に書く —— そのあと**提出**します（`knowledge`、`action: submit`、
  `base` と `path`）。ShuviX はその場で組み込みの `knowledge-writer` エージェントに確認させます：
  frontmatter（自己申告行、`type`、`title`、`description`、`tags`、`status`、`sources`）を補い、
  エントリが一つの主題だけを扱い、予備知識なしで読め、すべての主張に出典があるかを判定します。合格なら
  ShuviX が `generated`（提出者）と `verified`（ライターの機械確認）を押し、不合格なら報告が直すべき点を
  述べ、エントリは未確認のままです。ライターはこの経路でしか動きません —— `agent` ツールでは派遣
  できません —— そのモデルは通常の規則に従います（md の `shuvix-model`、なければ呼び出し元のもの）。
- **`edit` で変更**。パスは `search` / `list` が返した絶対パス —— 本文全体を送り直すより、精密な差分の
  方がよい。編集後、書き込みフックがファイルを検証し（診断はツール結果で返る）、`generated` を更新し、
  コミットし、サイドバーが更新されます。変更した内容は、もう一度提出するまで機械確認の対象外です。
- **手で**（Obsidian、ShuviX ノートブック、任意のエディタ）：メタデータ不要。ベース配下の人手による
  編集は次の走査で拾われ、次に観測される書き込みと共にコミットされます。サイドバーの**新規エントリ**は
  メタデータ一式（`type: Memory`、`status: draft`）を自分で `generated` 抜きで書き、actor は
  `human` です。

**エントリを見つけるのは二段階です。** `search` の索引にはエントリの*見出し面*だけ —— タイトル、
説明、タグ、type、そして本文中の**見出し行** —— が入り、散文は入りません。したがって結果が言うのは
「どれが主題に関係しそうか」であって、何が書いてあるかではありません：タイトルと説明を読んで合うものを
選び、そのファイルを `read` してください。（かつては本文全体を索引していました。ありふれた語ひとつでベースの
半分が返り、各ヒットが段落を引きずり、本当に欲しかったエントリが埋もれました。）本文中の文字列 ——
エラーメッセージ、シンボル、URL —— を探すには、どの一覧にも印字されるベースのディレクトリに対して
`grep` を使ってください。

`knowledge` ツールの操作：`bases`（このセッションが名指せるもの、各ベースのディレクトリ付き）、
`search`（自由テキスト。`base` を省くと有効なすべてのベースを対象にベースごとにグループ化 ——
インデックスは別々で、スコアはベース間で比較できない；中国語・日本語のテキストは索引前に分かち書き
される）、`list`（一つのベースの全ノート）、`submit`（上記）。一覧は絶対パスで返ります。リファレンス
ベース `shuvix` は読み取り専用：そこでの `submit` は拒否されます。ファイル書き込み
は止められませんが、確認されます（ask-on-external-path —— 読み取り専用のセッションディレクトリだから）。
いずれにせよ、同梱のファイルはアプリの更新で元に戻ります。

## 検証の段階

- 自己申告行を持つエントリ、または `type` を持つ任意のノート：厳格な OKF 検査 —— frontmatter や
  `type` の欠落は **error**；`title` / `description` の欠落、不正な `status`、日付でない `stale_after`、
  形の崩れた `generated` / `verified` / `sources`、ベース内で解決できないリンクは **warning**；
- それ以外のノート：YAML frontmatter が壊れているときだけ警告；
- 生成された `index.md` / `log.md`：検査しない。

書き込みフックの検証は受領票であって関門ではありません：壊れたエントリも書かれ、一覧されます。関門は
`submit` です —— 厳格な検査に通らないエントリにはスタンプを押しません。

## 何を記録するか

再び調べられるもの：決定とその理由、時間を食った落とし穴、コードが述べていない約束事、確認に手間の
かかった事実 —— その主題が属するベースへ書き、提出します。まず検索し、すでにその主題を扱っているエントリを広げる
（近い重複を足すのではなく）。リポジトリがすでに述べていること、今の会話にしか関係ないことは記録
しない。
