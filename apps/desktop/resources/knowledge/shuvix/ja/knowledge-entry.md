# ナレッジベースのエントリ

**ナレッジベース**は markdown のディレクトリ、**エントリ**はその中の一つの `.md` です。ShuviX は
Open Knowledge Format（OKF）v0.2 に、小さな独自プロファイルを添えて従います：frontmatter は
メタデータ、本文は知識、予約名は `index.md` と `log.md` だけです。

## ベースの場所

| ベース              | ディレクトリ                                                                              | `knowledge` ツールでの名前   |
| ------------------- | ----------------------------------------------------------------------------------------- | ---------------------------- |
| ユーザー自身の      | `~/.shuvix/knowledge/<name>/` —— **隠しでないサブディレクトリはすべて一つのベース**。マーカーファイル不要 | ディレクトリ名        |
| このプロジェクトの  | `~/.shuvix/knowledge-shuvix/projects/<projectId>/`（ツール経由で書かれ、手では書かない）    | `project`（予約名）          |
| ShuviX のリファレンス | アプリケーション内（読み取り専用、UI 言語ごと）                                          | `shuvix`（予約名）           |

ベースに必要なのはディレクトリだけです：ノートのフォルダをコピーして入れれば、それがベースです。
隠しファイルとディレクトリ（`.obsidian/`、`.trash/`、`.git/`）は決してベースの一部になりません。
各ベースは独自の git 履歴を持ちます：ShuviX が観測した最初の書き込みで（フォルダにリポジトリが
無ければ）`git init` し、その時点のフォルダをベースラインとし、以後観測されるすべての変更を
`kb(<op>): /path` として `Knowledge-Op` / `Knowledge-Actor` トレーラー付きでコミットします。

**セッションがどのベースを使うかはユーザーの選択です**（セッション設定 → ナレッジベース；プロジェクト
設定は新しいセッションの既定を決める）。未設定なら既定は、すべてのユーザーベース + （プロジェクト内
なら）プロジェクトのベース + `shuvix`。選択は固い境界です：`bases` は有効なものだけを一覧し、それ以外の
名前を名指すと拒否されます。システムプロンプトの `<knowledge_bases>` フェンスも同じ名前を一覧します。

## 広く読み、厳しく書く

- ベース内の隠しでない**すべての** `.md` は**ノート**です：サイドバーに並び、検索され、読めます ——
  タイトルは frontmatter の `title` → 最初の `# 見出し` → ファイル名。メタデータは不要で、ShuviX が
  ユーザーのノートを書き換えてメタデータを足すことはありません。
- ノートは、frontmatter がマッピングとして解析でき、空でない文字列の `type` を持ち、*他所の*
  `shuvix:` マーカーを持たないとき、加えて **OKF エントリ（概念）**でもあります（ベース内の
  `shuvix: agent v1` ファイルはノートであって概念ではない）。`knowledge` ツールの `create` が書く
  ものだけが、準拠を**保証**されています。
- `index.md` と `log.md` は OKF の予約名です。ShuviX はもう生成しません。以前に生成したものは
  形で隠され、手書きの同名ファイルは普通のノートです（決して概念ではない）。

## frontmatter キー（ShuviX プロファイル）

`create` が書く順に：

| キー            | 型                                                           | 必須                    | 意味                                                                                                                                                                                                                                       |
| --------------- | ------------------------------------------------------------ | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `shuvix`        | `okf v0.2`                                                   | いいえ                  | 自己申告：「これは OKF v0.2 で書かれた OKF エントリ」。ノートブックのプロパティカードはこれで選ばれる。無いノートも解析される。他の `shuvix:` 種別は「概念ではない」を意味する。                                                          |
| `type`          | 文字列                                                       | **はい**（概念には必須） | どんな種類のものか。ShuviX の開かれた語彙：`Memory`、`Concept`、`Entity`、`Decision`、`Guide`、`Source` —— 他の値も許され、そのまま表示される。                                                                                            |
| `title`         | 文字列                                                       | いいえ                  | 表示タイトル。既定：`.md` を除いたファイル名。                                                                                                                                                                                             |
| `description`   | 文字列                                                       | いいえ                  | **このエントリを開く価値があるのはいつかを述べる一行** —— `list` と `search` が表示するもので、後のセッションが読むかどうかを決める材料。                                                                                                     |
| `resource`      | 文字列                                                       | いいえ                  | エントリが表す外部ロケーター（まれ）。                                                                                                                                                                                                     |
| `tags`          | 文字列のリスト（カンマ区切り文字列も読める）                 | いいえ                  | 自由なタグ。                                                                                                                                                                                                                               |
| `status`        | `draft` \| `stable` \| `deprecated`                          | いいえ                  | **ライフサイクル**、既定 `stable`：`draft` = まだ不完全、`stable` = 頼れる、`deprecated` = リンクと履歴のために残す（検索から外れる）。`create` は明示的に書き出す。レビューのフラグでは**ない**。                                              |
| `stale_after`   | `YYYY-MM-DD`                                                 | いいえ                  | この日を過ぎるとエントリは再確認が必要（サイドバーにバッジ）。                                                                                                                                                                             |
| `sources`       | `{ id?, resource, title?, author?, last_modified? }` のリスト（素のロケーター文字列も可） | いいえ | 主張の出所。`resource` は自己完結したロケーター：絶対パス（`#symbol` 付き可）、完全な URL、`<remote-url>@<commit>:<path>`、または `shuvix://session/<id>`。`id` は脚注引用 `[^id]` を可能にする。                                        |
| `generated`     | `{ by, at }`                                                 | いいえ                  | **ホストのスタンプ** —— 最後にファイルを書いたのは誰か（`shuvix-<agent>/<model>`）、いつか（ISO 8601）。`create` が書き、エージェントの編集のたびに書き込みフックが更新する。手で設定しないこと。サイドバーの「新規エントリ」は意図的に省く。 |
| `verified`      | `{ by, at }` またはそのリスト                                | いいえ                  | **レビュー軸**：ユーザーがエントリを確認した記録。UI 操作だけが書ける —— **エージェントは決して書かない**。ここから信頼段階（未検証 / 機械確認 / 人手レビュー）と「検証後に編集」バッジ（`verified.at` が `generated.at` より古い）が導かれる。 |

未知のキーはそのまま保持されます。形が違う値は警告として報告され既定値に落ちます。frontmatter が
無いか、`type` が欠落・空のときだけ、ファイルは「概念ではない」ものになります。

## 本文

Markdown。**同じベース**内の他のエントリへは、バンドル絶対の markdown リンク ——
`[Agent 定義ファイル](/agent-md.md)`、ルートはベースのディレクトリ —— で。検証はベース内で解決
できないリンクに警告します。**別のベース**やセッションを指すには、パスではなく `shuvix://` URI を
使います（リンク検査はスキームを持つものを飛ばす）。見出し、コードフェンス、脚注は普通の markdown。
先頭の `# 見出し` は、frontmatter のないノートのタイトルを兼ねます。

## ファイル名

`create` はタイトルからファイル名を導きます：あらゆる文字体系の文字と数字は保持、それ以外の連続は `-`
に、ASCII は小文字化、60 文字で切り詰め、使用済みの名前には `-2`、`-3`、…（予約名も使用済み扱い）。
エントリは常にベースの**ルート**に置かれます。フォルダはユーザー自身の整理用で、サイドバーの
「新規エントリ」の置き場でもあります。

## エントリの書き方と変え方

- **`knowledge` ツールで作成**（`action: create`、`base`、`type`、`title`、`description`、`body`、
  任意で `tags` / `sources` / `stale_after` / `status`）。ホストが frontmatter（自己申告行、キー順、
  正規化された `type` / `status`、`generated`）を組み立て、ファイル名を付け、コミットし、絶対パスを
  返します。`write` でエントリを作らないこと —— メタデータを自分で正しく揃えることになります。
- **`edit` で変更**。パスは `search` / `list` / `read` / `create` が返した絶対パス —— 本文全体を送り
  直すより、精密な差分の方がよい。編集後、書き込みフックがファイルを検証し（診断はツール結果で返る）、
  `generated` を更新し、コミットし、サイドバーが更新されます。その後 `validate` を実行してください。
- **手で**（Obsidian、ShuviX ノートブック、任意のエディタ）：メタデータ不要。ベース配下の人手による
  編集は次の走査で拾われ、次に観測される書き込みと共にコミットされます。サイドバーの**新規エントリ**は
  `create` と同じメタデータ（`type: Memory`、`status: draft`）を `generated` 抜きで書き、actor は
  `human` です。

`knowledge` ツールの他の操作：`bases`（このセッションが名指せるもの）、`search`（自由テキスト。
`base` を省くと有効なすべてのベースを対象にベースごとにグループ化 —— インデックスは別々で、スコアは
ベース間で比較できない；中国語・日本語のテキストは索引前に分かち書きされる）、`list`（一つのベースの
全ノート）、`read`（バンドル相対パスで一つ、例 `/foo.md`）、`validate`（一つのノート、またはベース
全体）。リファレンスベース `shuvix` は読み取り専用：そこでの `create` は拒否され、ファイル書き込みは
ポリシーが拒みます。

## 検証の段階

- 自己申告行を持つエントリ、または `type` を持つ任意のノート：厳格な OKF 検査 —— frontmatter や
  `type` の欠落は **error**；`title` / `description` の欠落、不正な `status`、日付でない `stale_after`、
  形の崩れた `generated` / `verified` / `sources`、ベース内で解決できないリンクは **warning**；
- それ以外のノート：YAML frontmatter が壊れているときだけ警告；
- 生成された `index.md` / `log.md`：検査しない。

検証は受領票であって関門ではありません：壊れたエントリも書かれ、一覧されます。

## 何を記録するか

再び調べられるもの：決定とその理由、時間を食った落とし穴、コードが述べていない約束事、確認に手間の
かかった事実 —— その主題が属するベースへ。まず検索し、すでにその主題を扱っているエントリを改訂する
（近い重複を足すのではなく）。リポジトリがすでに述べていること、今の会話にしか関係ないことは記録
しない。
