# ナレッジベースのエントリ

**ナレッジベース**は markdown のディレクトリ、**エントリ**はその中の一つの `.md` です。ShuviX は
Open Knowledge Format（OKF）v0.2 に、小さな独自プロファイルを添えて従います：frontmatter は
メタデータ、本文は知識、予約名は `index.md` と `log.md` だけです。

## ベースの場所

| ベース              | ディレクトリ                                                                              | `knowledge` ツールでの名前   |
| ------------------- | ----------------------------------------------------------------------------------------- | ---------------------------- |
| ユーザー自身の      | `~/.shuvix/knowledge/<name>/` —— **隠しでないサブディレクトリはすべて一つのベース**。マーカーファイル不要 | ディレクトリ名        |
| このプロジェクトの  | `~/.shuvix/knowledge-shuvix/projects/<projectId>/`（ナレッジ司書が書き、手では書かない）    | `project`（予約名）          |
| この bot の         | `~/.shuvix/knowledge-shuvix/bots/<key>/`、`<key>` は bot の身元から —— その `shuvix-id`、ファイルになければ `name-<名前>`（ナレッジ司書が書き、手では書かない） | `bot`（予約名）              |
| ShuviX のリファレンス | アプリケーション内（読み取り専用、UI 言語ごと）                                          | `shuvix`（予約名）           |

ベースに必要なのはディレクトリだけです：ノートのフォルダをコピーして入れれば、それがベースです。
隠しファイルとディレクトリ（`.obsidian/`、`.trash/`、`.git/`）は決してベースの一部になりません。
各ベースは独自の git 履歴を持ちます：ShuviX が観測した最初の書き込みで（フォルダにリポジトリが
無ければ）`git init` し、その時点のフォルダをベースラインとし、以後観測されるすべての変更を
`kb(<op>): /path` として `Knowledge-Op` / `Knowledge-Actor` トレーラー付きでコミットします。

**プロジェクト内のセッションには、そのプロジェクトのベース `project` が常に付き、先頭に並びます** ——
プロジェクトについて分かったことはそこに記録するので、チェックするものではありません（設定カードにも
出ません）。**それ以外のベースはユーザーの選択です**（セッション設定 → 拡張機能のナレッジベース行、
または入力欄のツール選択；プロジェクト設定は新しいセッションの既定を決める）。**bot 自身のセッションにも同じく、その bot のベース `bot` が常に付き**、`project` のすぐ後に並びます（`bot-md` エントリを参照）：
bot の定時実行や、そのセッションが派遣したエージェントにも付き、bot が開いたサブセッションには付きません。未設定なら親セッション、
次にプロジェクトの既定に従い、誰も選んでいなければ自分のベースはどれも有効になりません。**どのセッションにも常に `shuvix` が付きます**（最後に並びます）。`project`・`bot` と同じくチェックするものではなくカードにも出ないので、エージェントはいつでも ShuviX 自身のファイルの書き方を調べられます。選択は固い境界です：`bases` は有効なものだけを一覧し、それ以外の名前を名指すと拒否されます。システムプロンプトの
`<knowledge_bases>` フェンスも同じ名前を一覧します。

**ナレッジ司書以外のエージェントには、ベースのディレクトリは見えません。** それらにとってベースは
その名前であり、エントリはベース内のパス（`/auth/session.md`）です：`knowledge` ツールでエントリを
`search`・`list`・`read` し、残す価値のあるものは `submit` で司書に渡します（後述）。これはツールと
プロンプトの約束事であって錠ではありません：別の方法でディレクトリを見つけたエージェントを止めるものは
ありません。

選択は、セッションが確認なしに触れられる範囲も決めます。有効なベースはセッションの権限表の**読み書き
できる**行です（`policy-md` エントリの `vars.aclWrite`）—— 司書は提出したセッションの中で動き、
ファイルツールで書くので、そこでのファイルの読み取り・作成・移動・削除は確認なしです。ベースの変更は
すべてそのベース自身の git にコミットされ、元に戻せます。`shuvix` は**読み取り専用**の
行（`vars.aclRead` にだけある）です。有効でないベースはホームフォルダの
他のフォルダと同じで、読むときに確認が出ます。

## 広く読み、厳しく書く

- ベース内の隠しでない**すべての** `.md` は**ノート**です：サイドバーに並び、検索され、読めます ——
  タイトルは frontmatter の `title` → 最初の `# 見出し` → ファイル名。メタデータは不要で、ShuviX が
  ユーザーのノートを書き換えてメタデータを足すことはありません。
- ノートは、frontmatter がマッピングとして解析でき、空でない文字列の `type` を持ち、*他所の*
  `shuvix:` マーカーを持たないとき、加えて **OKF エントリ（概念）**でもあります（ベース内の
  `shuvix: agent v1` ファイルはノートであって概念ではない）。`submit` のあとにナレッジ司書が報告し、
  そのうえで厳格な検査に通ったエントリだけが、ShuviX の機械確認を持ちます。
- `index.md` と `log.md` は OKF の予約名です。ShuviX はもう生成しません。以前に生成したものは
  形で隠され、手書きの同名ファイルは普通のノートです（決して概念ではない）。

## frontmatter キー（ShuviX プロファイル）

ふつうの順に：

| キー            | 型                                                           | 必須                    | 意味                                                                                                                                                                                                                                       |
| --------------- | ------------------------------------------------------------ | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `shuvix`        | `okf v0.2`                                                   | いいえ                  | 自己申告：「これは OKF v0.2 で書かれた OKF エントリ」。ノートブックのプロパティカードはこれで選ばれる。無いノートも解析される。他の `shuvix:` 種別は「概念ではない」を意味する。                                                          |
| `type`          | 文字列                                                       | **はい**（概念には必須） | どんな種類のものか。ShuviX の開かれた語彙：`Memory`、`Concept`、`Entity`、`Decision`、`Guide`、`Source` —— 他の値も許され、そのまま表示される。                                                                                            |
| `title`         | 文字列                                                       | いいえ                  | 表示タイトル。既定：`.md` を除いたファイル名。                                                                                                                                                                                             |
| `description`   | 文字列                                                       | いいえ                  | **このエントリを開く価値があるのはいつかを述べる一行** —— `list` と `search` が表示するもので、後のセッションが読むかどうかを決める材料。                                                                                                     |
| `resource`      | 文字列                                                       | いいえ                  | エントリが表す外部ロケーター（まれ）。                                                                                                                                                                                                     |
| `tags`          | 文字列のリスト（カンマ区切り文字列も読める）                 | いいえ                  | 自由なタグ。                                                                                                                                                                                                                               |
| `status`        | `draft` \| `stable` \| `deprecated`                          | いいえ                  | **ライフサイクル**、既定 `stable`：`draft` = まだ不完全、`stable` = 頼れる、`deprecated` = リンクと履歴のために残す（検索から外れる）。提出時に明示的に書き出される。レビューのフラグでは**ない**。                                              |
| `stale_after`   | `YYYY-MM-DD`                                                 | いいえ                  | この日を過ぎるとエントリは再確認が必要（サイドバーにバッジ）。                                                                                                                                                                             |
| `sources`       | `{ id?, resource, title?, author?, last_modified? }` のリスト（素のロケーター文字列も可） | いいえ | 主張の出所。`resource` は自己完結したロケーター：絶対パス（`#symbol` 付き可）、完全な URL、`<remote-url>@<commit>:<path>`、または `shuvix://session/<id>`。`id` は脚注引用 `[^id]` を可能にする。                                        |
| `generated`     | `{ by, at }`                                                 | いいえ                  | **ホストのスタンプ** —— 内容を書いたのは誰か（`shuvix-<agent>/<model>`）、いつか（ISO 8601）。エージェントがエントリを編集するたびに書き込みフックが更新し、`submit` のあとに司書が報告したエントリでは提出したエージェントに書き換わる。手で設定しないこと。サイドバーの「新規エントリ」は意図的に省く。 |
| `verified`      | `{ by, at }` またはそのリスト                                | いいえ                  | **レビュー軸**：誰がエントリを確認したか。人による確認（`by: human:…`）は UI 操作だけが書く。`submit` のあとに司書が報告した各エントリには、その機械確認（`by: shuvix-knowledge-writer/<model>`、以前のものを置き換える）が付く。**エージェントは決して書かない。** ここから信頼段階 —— 機械確認か人手レビューか、`generated.at` より古くない確認だけを数える —— と「確認後に編集あり」バッジ（すべての確認が `generated.at` より古い）が導かれる。 |

未知のキーはそのまま保持されます。形が違う値は警告として報告され既定値に落ちます。frontmatter が
無いか、`type` が欠落・空のときだけ、ファイルは「概念ではない」ものになります。

## 本文

Markdown。**同じベース**内の他のエントリへは、バンドル絶対の markdown リンク ——
`[Agent 定義ファイル](/agent-md.md)`、ルートはベースのディレクトリ —— で。検証はベース内で解決
できないリンクに警告します。**別のベース**やセッションを指すには、パスではなく `shuvix://` URI を
使います（リンク検査はスキームを持つものを飛ばす）。見出し、コードフェンス、脚注は普通の markdown。
先頭の `# 見出し` は、frontmatter のないノートのタイトルを兼ねます。

## ファイル名

司書はエントリのファイルを主題にちなんで名付け、後で改名や移動をすることもあり、そのときは古い名前を
指していたリンクを直します。ベース内では、`write` はエージェントが読んでいない既存ファイルの上書きを拒否するので、
使用済みの名前を選んでも他人のエントリが黙って置き換わることはありません。サイドバーの**新規エントリ**は
タイトルからファイル名を導きます：あらゆる文字体系の文字と数字は保持、それ以外の連続は `-` に、ASCII は
小文字化、60 文字で切り詰め、使用済みの名前には `-2`、`-3`、…（予約名も使用済み扱い）。

## エントリの書き方と変え方

- **提出します**（`knowledge`、`action: submit`、`base` と `content`）：何が成り立つか、各主張の
  出どころ（パス、URL、コミット）を述べる普通の markdown。あるエントリを訂正・拡張するものなら `entry`
  も付けます。ShuviX はその場で、提出した会話の中で組み込みのナレッジ司書（`knowledge-writer`
  エージェント）に処理させます。ベースに書き込むのは司書だけで、提出は司書にとって提案であり命令では
  ありません：あとのセッションが必要とし、リポジトリからは読み取れないものだけを残すので（下の
  「何を記録するか」）、提出の一部だけを記録することも —— 調査なら結論だけで、そこに至る手順は残さない ——
  受け取らないこともあり、何を残したか・なぜかを伝えます。司書はベースにすでに何があるかを読み、残す
  内容をどう記録するかを決めます —— 新しいエントリ、または既存エントリの変更（拡張、訂正、分割、統合、
  改名、移動、`deprecated` にする、削除）。あわせて、提出が届いたあたりを整えます：同じ件のエントリは
  一つにまとめ、残る価値のないエントリは残る部分をその件のエントリに移してから削除し、エントリが 12 個
  ほどを超えたフォルダは主題ごとのフォルダに分けます。そして触れたエントリと短い報告を返します。
  書き込みはベースのディレクトリ内でファイルツール（`read`、`write`、`edit`、`move`、`delete`、`grep`）
  を使い、書くエントリにはすべて上記の frontmatter を付け、ユーザー自身のノート（frontmatter のない
  ファイル）はそのままにし、人が確認したエントリは統合で消したり削除したりせず、提出の事実を確かめる
  ためにベースの外のものを開くことは決してありません。そのあと ShuviX は、司書が報告したエントリのうち
  厳格な検査に通るものそれぞれに `generated`（提出者）と `verified`（司書の機械確認）を押します。移動や
  改名だけのエントリ（本文が変わっていないもの）は元の印のままです。司書は `knowledge` ツール経由でしか
  動きません —— `agent` ツールでは派遣できません —— そのモデルは通常の規則に従います（md の
  `shuvix-model`、なければ呼び出し元のもの）。何を残すか、ベースをどう整理するかを変えるには
  `~/.shuvix/agents/knowledge-writer.md` を上書きしてください。
- **司書にベースを整理させます**（`knowledge`、`action: organize`、`base`。ユーザーの具体的な要望が
  あれば `content` に）：すでに散らかったベース向けです。何も提出しません。司書が同じやり方でベース全体を
  見直し —— 同じ件のエントリを統合し、残る価値のないものを削除し、残りを主題ごとのフォルダに分け、
  リンクを直し —— 何を変えたかを報告します。変更はどれもベース自身の git 履歴のコミットなので、
  元に戻せます。司書が書き直したエントリは `generated` も `verified` も司書になり、移動だけのエントリは
  元の印のままです。
- **別のプロジェクトから移行します**（`knowledge`、`action: migrate`、`project`・`entries`・`base`）：
  プロジェクトを分けるとき、新しいプロジェクトのセッションのエージェントが、別のプロジェクト自身の
  ベースからエントリを持ってきます。ShuviX が指定されたエントリを読み、受け取る側のベースの司書に
  そのまま渡します —— エージェントは本文を写しません。司書は 1 件ずつ、そのまま受け取る、その件を
  すでに扱うエントリに統合する、受け取らない、のいずれかを決め、受け取ったものを報告します。ShuviX は
  司書が書いたエントリに提出のときと同じ印を押し、司書が受け取ったエントリだけを別のプロジェクトの
  ベースから削除します。選ぶときは、まず `list`・`search`・`read` に `project`（別のプロジェクトの名前）を
  付けてそのベースを見ます。そのベースはこのセッションの権限表の外にあるので、読むときと変更するときに
  それぞれ先に確認されます。プロジェクトの分け方は `moving-sessions` エントリを参照してください。
- **手で**（Obsidian、ShuviX ノートブック、任意のエディタ）：メタデータ不要。ベース配下の人手による
  編集は次の走査で拾われ、次に観測される書き込みと共にコミットされます。サイドバーの**新規エントリ**は
  メタデータ一式（`type: Memory`、`status: draft`）を自分で `generated` 抜きで書き、actor は
  `human` です。

**エントリを見つけるのは二段階です。** `search` の索引にはエントリの*見出し面*だけ —— タイトル、
説明、タグ、type、そして本文中の**見出し行** —— が入り、散文は入りません。したがって結果が言うのは
「どれが主題に関係しそうか」であって、何が書いてあるかではありません：タイトルと説明を読んで合うものを
選び、そのエントリを `read` してください。（かつては本文全体を索引していました。ありふれた語ひとつでベースの
半分が返り、各ヒットが段落を引きずり、本当に欲しかったエントリが埋もれました。）

`knowledge` ツールの操作：`bases`（このセッションが名指せるもの）、
`search`（自由テキスト。`base` を省くと有効なすべてのベースを対象にベースごとにグループ化 ——
インデックスは別々で、スコアはベース間で比較できない；中国語・日本語のテキストは索引前に分かち書き
される）、`list`（一つのベースの全ノート）、`read`（ベース内のパスで一つのエントリ、長いものは
`offset` / `limit`）、`submit`・`organize`・`migrate`（上記）。結果はエントリをベース内のパスで示し、
ベースのディレクトリも見えるのは司書の呼び出しだけです。リファレンスベース `shuvix` は読み取り専用：
そこでの `submit` と `organize` は拒否されます。いずれにせよ、同梱のファイルはアプリの更新で元に
戻ります。

## 検証の段階

- 自己申告行を持つエントリ、または `type` を持つ任意のノート：厳格な OKF 検査 —— frontmatter や
  `type` の欠落は **error**；`title` / `description` の欠落、不正な `status`、日付でない `stale_after`、
  形の崩れた `generated` / `verified` / `sources`、ベース内で解決できないリンクは **warning**；
- それ以外のノート：YAML frontmatter が壊れているときだけ警告；
- 生成された `index.md` / `log.md`：検査しない。

書き込みフックの検証は受領票であって関門ではありません：壊れたエントリも書かれ、一覧されます。関門は
`submit` のあとのスタンプです —— ShuviX は厳格な検査に通らないエントリにはスタンプを押しません。

## 何を記録するか

記録するのは、数か月後にこの件に取り組む人 —— この会話にいなかった人 —— が必要とし、リポジトリからは
読み取れないものだけです：決定とその理由、システムやその周辺の制限・挙動でコードが述べていないもの、
また踏むことになる落とし穴（原因と見分け方）、取り決めやユーザーの継続的な好み、繰り返し行う作業の
やり方。その主題が属するベースへ `submit` で渡し、「何が起きたか」ではなく「何が成り立つか」として
書きます。まず検索し、提出がすでにその主題を扱っているエントリを広げるものなら、そのエントリを名指して
ください。

知識ではなく、司書も受け取らないもの：作業の記録（何をした・変えた・試した・テストした、どのファイルと
コミットか —— リポジトリの履歴にあります）、すでに直った問題（直したあとも成り立ち、今後の作業を縛る
ものがある場合を除く）、ある時点の状態（進捗、ToDo、計画、テストの実行結果、計測値）、コードがすでに
語っていること、ベースにすでにあること。ほとんどのタスクには提出するものがありません。司書が一部だけを
残したり受け取らなかったりしたときは、その説明をユーザーに伝え、もう一度提出しないでください。
