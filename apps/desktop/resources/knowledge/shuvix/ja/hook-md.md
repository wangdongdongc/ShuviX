# Hook ファイル

**hook** が言うことは一つだけです：*これらのトリガーポイントで、この条件が成り立つとき、この
エージェントを派遣し、このテキストを渡す*。ShuviX はテキストにイベントを添えます。エージェントの答えが
どう扱われるかは、バインドされたトリガーポイントの種類で決まります：

- **観察型**トリガー（`session.*`）：**ホストはエージェントの結果を決して読みません** —— hook は観察者で
  あって、介入者ではありません。トリガーとなった出来事を止めることも、書き換えることも、遅らせることも
  できず、エージェントは自分のツールで行動します。
- **判定型**トリガー（`permission.request`）：エージェントは `next` ツールで構造化された結果を返さなければ
  ならず、ShuviX はその答えに従って動きます。判定型トリガーは ShuviX がもともと確認のために止まる場所に
  しかありません —— hook が決めるのは*誰が*答えるかであって、確認する*かどうか*ではありません。

ファイル形式はどちらも同じです。判定型トリガーにバインドすれば、そのファイルは判定として実行されます。

- 場所：`~/.shuvix/hooks/<name>.md`。
- マーカー：`shuvix: hook v1` —— **必須**（マーカー導入前の hook ファイルは存在しないので、これがない
  ファイルは迷い込んだノートでしかありえません）。`hook` と `hook v2` も受け付けます。バージョンは
  検査されません。
- 存在すれば有効、トリガーのたびに読み直されます。組み込みは二つ：`auto-title` と `auto-review`。

## 例

```markdown
---
shuvix: hook v1
name: capture-decisions
description: After each turn in a project session, keep any decision worth keeping.
shuvix-hook-agent: knowledge-writer
shuvix-hook-on:
  - trigger: session.turn-completed
    when: event.profileName == 'work' && event.textMessageCount >= 2
---

Read `recentText` in the event below. If it holds a decision about this project, record it
in the `project` knowledge base. Otherwise finish without writing.
```

## frontmatter キー

| キー                  | 型                 | 必須   | 意味                                                                                                                                                                              |
| --------------------- | ------------------ | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `shuvix`              | `hook v1`          | **はい** | ファイル種別マーカー。                                                                                                                                                          |
| `name`                | 文字列             | いいえ | 身元。既定値はファイルのベース名。                                                                                                                                                |
| `shuvix-displayName`  | 文字列             | いいえ | サイドバーの「フック」グループのラベル。既定値は `name`。                                                                                                                                           |
| `description`         | 文字列             | いいえ | 設定一覧の一行。                                                                                                                                                                  |
| `shuvix-id`           | 文字列             | いいえ | オブジェクト ID —— ファイルをどこへ移しても、ShuviX はこれで識別します。ShuviX が作成するファイルでは UUID、同梱ファイルでは `<種類>:builtin:<名前>`。コピーは元と同じ ID を共有します。ShuviX が書き込むので触れないでください。不正な値は警告が出るだけで、ファイル全体は拒否されません。  |
| `shuvix-hook-agent`   | 文字列             | **はい** | 派遣するエージェントを `name` で：任意の組み込みエージェント、または `~/.shuvix/agents/<name>.md`。**ベース人格は不可**（`work` / `chat` / `notebook` / `bot`）—— 解析時に拒否。   |
| `shuvix-hook-on`      | バインディングのリスト | **はい** | 少なくとも一つの `{ trigger, when? }`。`trigger` はトリガーポイント id、`when` は省略可能な CEL 式。他のキーを持つバインディングは拒否。                                          |

厳格さ（ファイル全体を拒否、サイドバーの「フック」グループに琥珀色の行として表示され、理由はツールチップ）：マーカー欠落、`shuvix-hook-agent` の欠落・
空、エージェントがベース人格、`shuvix-hook-on` の欠落・空・非リスト、`trigger` のないバインディングや
余分なキーを持つバインディング、文字列でないか CEL として解析できない `when`、素の `on:` / `agent:`
キー（接頭辞付きの名前だけが読まれる —— 綴りを誤ったキーが黙って「バインディングなし」を意味しては
ならない）、そして上記二つ以外のあらゆる `shuvix-hook-*` キー。**未知のトリガー id はエラーでは
ありません**：バインディングは保持されますが不活性で、警告が付きます。トリガーの語彙はリリースごとに
増えるからです。空または `~` の `when` は「条件なし」を意味します。

## 本文 —— タスクのテキスト

frontmatter の後の全部が、エージェントに渡される文章です。空でもかまいません（エージェント自身の
ファイルがすでに何をすべきか述べているとき）。**テンプレート構文はありません**：プレースホルダーも
変数もありません。イベントはランタイムが固定のフェンスの中に YAML として添えます：

```text
<body>

<hook_event trigger="session.turn-completed">
sessionId: …
profileName: work
title: …
isDefaultTitle: false
turnCount: 3
textMessageCount: 5
titleAutoGenerated: true
recentText: |
  User: …
  Assistant: …
</hook_event>
```

エージェントに特定のフィールドを見せたいなら、本文でそれを名指します（「抜粋は `recentText` にある」）。

## トリガーポイント

すべてのトリガーは**セッションスコープ**です：実行は必ずどれかのセッションの下で派遣されます。二つの
`session.*` トリガーは通常のチャットセッションが発します（ノートブックセッションは発しません）。
`permission.request` は、どのセッションでも、エージェントのツール呼び出しが確認に至ったところで発します。
ペイロードには、発する場所が自然に持っている事実だけが入ります：

| トリガー                   | 種類   | いつ                                                                                                    | ペイロード                                                                                                                                                                                                                                       |
| -------------------------- | ------ | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `session.prompt-accepted`  | 観察型 | ユーザーのプロンプトが検証を通り、ルートエージェントに渡される直前（モデルはまだ動いていない）           | `sessionId`、`profileName`（`work` / `chat` / `bot`、またはサブセッションに固定されたエージェント）、`title`、`isDefaultTitle`（タイトルがまだ汎用の既定値）、`promptText`                                                                     |
| `session.turn-completed`   | 観察型 | ツール呼び出しを含む一ターン全体が終了 —— **成功・失敗・中断のいずれでも発火**                            | 共通の四フィールドに加え、`turnCount`（これまでのユーザーテキストメッセージ数、今回を含む）、`textMessageCount`（空でないユーザー + アシスタントのメッセージ数）、`titleAutoGenerated`（タイトルが自動化由来である間 `true`）、`recentText`（会話の末尾、約 1000 文字） |
| `permission.request`       | 判定型 | セキュリティポリシーが操作の判断を求め（effect が `ask`）、承認カードが表示される直前                     | 下記参照                                                                                                                                                                                                                                         |

トリガーの追加は ShuviX 側の変更です（トリガー表に一行と、一つの emit）。hook が発明することは
できません。

## `permission.request` —— 承認リクエストに答える

発火するのは effect が `ask` の規則だけです。`force-ask` の規則は「ユーザーだけが答える」という意味で、
`deny` はそのまま拒否し、`force-allow` はそのまま通します —— いずれも hook には届きません（組み込み
ポリシーはどれも使いませんが、あなた自身のポリシーは使えます）。ユーザーが「許可して記憶」と答えた
パスはそもそも確認されません：組み込みのパスの規則がそれを除外しています。
判定型 hook が派遣したエージェント自身の確認はそのままユーザーに渡るので、レビュアーが自分自身を
レビューすることはありません。

ペイロードは、レビューするエージェントが受け取るもののすべてです。人が書いたものと操作そのものだけを
運び、作業中のエージェント自身の文章やツール出力は決して入りません：

- `sessionId` —— 操作が行われるセッション（実行はその下で派遣されます）。
- `agent` —— 確認を求めたエージェントの `profile`（エージェント名）と `kind`（`root` / `spawned`）。
- `operation` —— `tool`（その操作付き、例：`session: create-sub-session`）、`action`（`read` / `write` /
  `execute` / `navigate`）、`objectType`（`command` / `path` / `database` / `gitTool` / `url` /
  `invocation`）、`target`（コマンド、パス、SQL、URL。切り詰めあり）、そして `facts`：コマンドなら
  `channel`、`host`（ssh）、`sandboxed`、`unconfinedReason`、`background`。パスなら `path`、
  `requestedPath`、`diff`（切り詰めあり）、`isNewFile`。データベースなら `connection`、`dbType`、
  `readonly`。url なら `scheme`、`host`、`browser`。常に `workingDirectory` と `platform`。
- `policy` —— 確認を求めたポリシーの `names` と、それらをまとめた `prompt`。
- `userMessages` —— 人が書いたもの、古い順：人のメッセージ、エージェントの質問への答え、承認カードに
  書いたフィードバック（最初の一件と最新の八件、それぞれ切り詰め）。サブセッションでは、それが属する
  最上位の会話から取ります。
- `delegatedTasks` —— サブセッションのみ：親エージェントが送ったタスク（主張であって許可ではない）。
  それ以外では空。
- `recentOperations` —— このセッションで最近下された判定、最大十件。各 `{ target, outcome }`。

答えは `next` ツールの引数で、固定のスキーマで検査されます：
`{ decision: allow | ask | deny, risk: low | medium | high | critical, summary, reason }`。

- `allow` —— カードを出さずに実行。`deny` —— 拒否され、エージェントは `reason` を読みます。`ask` ——
  レビュアーの `risk`、`summary`、`reason` を添えてカードを表示。
- 一致した複数の hook は並行して動き、最も厳しい答えが勝ちます（`deny` > `ask` > `allow`）。
- 答えがない —— タイムアウト、停止、実行の失敗、不正な結果、一致する hook なし —— ときはユーザーに
  確認します。壊れた答えが許可に変わることはありません。
- 同じセッションで三回続けて、または累計二十回拒否されると、そのセッションの確認はそのままユーザーに
  渡ります。ユーザーが確認に一度答えると、連続回数はリセットされます。

## `when` フィルター

CEL（Common Expression Language —— セキュリティポリシーを評価するのと同じエンジンですが、`inDir` の
ようなポリシー関数はありません）。次のコンテキストで**ブール値**に評価されなければなりません：

- `event` —— 上のペイロード**に加えて** `trigger`（トリガー id。したがって `trigger` は予約された
  ペイロードキー）。入れ子のフィールドはドットで読みます：`event.operation.objectType == 'command'`、
  `event.operation.facts.unconfinedReason == 'escalated'`；
- `env` —— `{ host: 'desktop' | 'extension', platform: 'darwin' | 'win32' | 'linux' }`。

ペイロードに無いフィールドを読むのはエラーで、エラーは**不一致**を意味します（警告付き）—— hook が
誤って発火することはありません。省略可能なフィールドは `has(event.field)` で守ってください。

## ランタイム規則（ホスト側、ファイルには書かない）

- 一回の実行 = 名指されたエージェントを**イベントを発したセッションの下で**一度派遣すること ——
  `agent` ツールと同じ経路なので、ツール、確認、LLM ログ、サブエージェントパネルはすべてその
  セッションに落ち、すべてのツール呼び出しが同じセキュリティポリシーを通ります。モデルと思考レベル =
  セッションの現在のもの。ただしエージェントファイルの `shuvix-model` / `shuvix-thinking` が優先。
  hook 自身はどちらも選びません。**未知のエージェント / 使えるモデルなし**：理由をログしてスキップ
  （設定の誤りであり、失敗した実行ではありません）。
- **観察型トリガー**：この hook のこのセッションでの実行がまだ続いている間、新しいトリガーはスキップ
  されます（`busy`）。タイムアウトは 5 分で、実行は中断されます。エージェントの答えは捨てられます ——
  残すべきものは、自分のツールでそうしなければなりません（ナレッジベースへ記録する、`session` ツールで
  セッションのタイトルを設定する、……）。
- **判定型トリガー**：重複排除はしません —— 確認の一つ一つがそれぞれの判定です。タイムアウトは 60 秒。
  答えは `next` からだけ読み、エージェントの文章は決して読みません。
- 実行は所属セッションのサブエージェントパネルとメインプロセスのログ（`hook "<name>" run=… start / ok
  / failed`、`skipped …: busy | unknown-agent | no-model`）に見えます。ジャーナルファイルはありません。
- セッションの削除は、その hook の実行を中断します。ツール呼び出しを停止すると、それが待っている
  レビューも中断されます。

## 組み込み hook と上書き

`auto-title` は `session.prompt-accepted when event.isDefaultTitle` と `session.turn-completed when
event.titleAutoGenerated && event.turnCount == 2 && event.textMessageCount >= 3` で `titler`
エージェントを名指します。titler は `session` ツールの `set-title` でタイトルを適用します。

`auto-review` はすべての `permission.request` で `permission-reviewer` エージェントを名指します。この
エージェントはツールを持たず、`shuvix-thinking: low` を宣言しており（思考をオフにすると、`next` を呼ばずに判定を本文に書いてしまうモデルがあるため）、そのファイルがレビューの規則です。
派遣するのは ShuviX だけです：`agent` ツールからは派遣できず、それでサブセッションを開くこともできません。

同名のユーザーファイルは組み込み hook を丸ごと置き換えます。一部の操作だけをレビューさせたいなら、`auto-review` に `when` を付けます（例：
`event.operation.objectType != 'command'`）。判断のしかたを変えたいなら、上書きするのはエージェントの
方です：`~/.shuvix/agents/permission-reviewer.md`。エージェントによる `~/.shuvix/hooks`、`agents`、
`policies`、`skills` への書き込みは、確認が出る普通の書き込み（ask-on-external-path —— どれも書き込み
できるセッションディレクトリではない）です：レビュアーは ShuviX 自身の保護を書き換えるものを拒否
するよう指示されており、サンドボックス内のコマンドはそこへそもそも書けません。
そうした書き込みを必ずユーザーに届けたいなら、`vars.shuvixConfigDirs` に対する `force-ask` のポリシーを
書きます（`policy-md` を参照）。同名のコピーは `shuvix-files` エントリの規則に従います。

## 意図的に無いもの

スクリプトブロック、オーケストレーションのプリミティブ、ファイル内の結果スキーマ（判定型トリガーは
自前のものを持っています）、プロンプトテンプレート、並行数やタイムアウトのキー、ジャーナルはありません。
観察型 hook は何も止められず、判定型 hook は ShuviX がもともと確認のために止まる場所にしかありません。
セッションが次に何をするかを*変える*必要のあるタスクは hook ではありません —— エージェント自身の
プロンプトか、セキュリティポリシーに属します。
