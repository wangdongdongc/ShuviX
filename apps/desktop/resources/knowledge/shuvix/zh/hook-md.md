# Hook 文件

一份 **hook** 只说一件事：*在这些触发点上、当这个条件成立时，派发这个 agent，并把这段话交给它*。
ShuviX 把事件附在那段话后面。agent 的回答怎么处理，取决于它绑的触发点是哪一类：

- **观察型**触发点（`session.*`）：**宿主从不读 agent 的结果** —— hook 是观察者，不是拦截者。它拦不住、
  改不了、也拖不慢触发它的那件事；agent 用自己的工具做事。
- **判定型**触发点（`permission.request`）：agent 必须经 `next` 工具交回一份结构化结果，ShuviX 按它行事。
  判定型触发点只出现在 ShuviX 本来就要停下来询问的地方 —— hook 决定的是*谁*来回答，从不决定*要不要*问。

两类的文件格式完全一样：把文件绑到判定型触发点上，它就按判定的方式运行。

- 位置：`~/.shuvix/hooks/<name>.md`。
- 标记：`shuvix: hook v1` —— **必需**（不存在标记引入之前的 hook 文件，没有它的只可能是误投的笔记）。
  `hook` 与 `hook v2` 也认；版本不检查。
- 存在即生效，每次触发时重新读取。两个内置：`auto-title` 与 `auto-review`。

## 示例

```markdown
---
shuvix: hook v1
name: capture-decisions
description: After each turn in a project session, keep any decision worth keeping.
shuvix-hook-agent: knowledge-writer
shuvix-hook-on:
  - trigger: session.turn-completed
    when: event.profileName == 'work' && event.textMessageCount >= 2
---

Read `recentText` in the event below. If it holds a decision about this project, record it
in the `project` knowledge base. Otherwise finish without writing.
```

## frontmatter 键

| 键                    | 类型       | 必填   | 含义                                                                                                                                                        |
| --------------------- | ---------- | ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `shuvix`              | `hook v1`  | **是** | 文件类型标记。                                                                                                                                              |
| `name`                | 字符串     | 否     | 身份；缺省取文件基础名。                                                                                                                                    |
| `shuvix-displayName`  | 字符串     | 否     | 侧栏「Hooks」分组里的标签。缺省 = `name`。                                                                                                                       |
| `description`         | 字符串     | 否     | 设置列表里的一句话。                                                                                                                                        |
| `shuvix-hook-agent`   | 字符串     | **是** | 要派发的 agent，按 `name`：任何内置 agent 或 `~/.shuvix/agents/<name>.md`。**绝不能是基座人格**（`work` / `chat` / `notebook` / `bot`）—— 解析时拒绝。       |
| `shuvix-hook-on`      | 绑定列表   | **是** | 至少一条 `{ trigger, when? }`。`trigger` 是触发点 id；`when` 是可选的 CEL 表达式。绑定里出现别的键即拒绝。                                                    |

严格性（整份拒绝，以琥珀色行列在侧栏「Hooks」分组、悬停可见原因）：缺标记、`shuvix-hook-agent` 缺失或为空、agent 是基座人格、
`shuvix-hook-on` 缺失 / 为空 / 不是列表、某条绑定没有 `trigger` 或带了多余的键、`when` 不是字符串或
不是合法 CEL、裸的 `on:` / `agent:` 键（只读带前缀的名字 —— 写错的键名不能静默变成「没有绑定」），
以及任何不是上述两个的 `shuvix-hook-*` 键。**未知的触发点 id 不算错**：绑定保留但惰性化，并记一条警告，
因为触发点词汇表随版本增长。`when` 留空或写 `~` 表示「没有条件」。

## 正文 —— 任务文本

frontmatter 之后的全部内容就是交给 agent 的那段话。可以为空（agent 自己的文件已经说清要做什么时）。
**没有模板语法**：没有占位符，没有变量。事件由运行时以 YAML 附在一个固定围栏里：

```text
<body>

<hook_event trigger="session.turn-completed">
sessionId: …
profileName: work
title: …
isDefaultTitle: false
turnCount: 3
textMessageCount: 5
titleAutoGenerated: true
recentText: |
  User: …
  Assistant: …
</hook_event>
```

想让 agent 只看某个字段，在正文里点名它（「摘录在 `recentText` 里」）。

## 触发点

所有触发点都是**会话域**的：一次运行总是派发在某条会话之下。两个 `session.*` 触发点由普通聊天会话发出
（笔记本会话不发）；`permission.request` 在任何会话里、只要 agent 的工具调用走到询问就会发出。载荷只放
发出方天然持有的事实：

| 触发点                     | 类型   | 何时                                                                                       | 载荷                                                                                                                                                                                                                     |
| -------------------------- | ------ | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `session.prompt-accepted`  | 观察型 | 一条用户 prompt 通过校验、即将交给根 agent（模型尚未开始）                                  | `sessionId`、`profileName`（`work` / `chat` / `bot`，或子会话钉下的 agent）、`title`、`isDefaultTitle`（标题仍是通用缺省值）、`promptText`                                                                                 |
| `session.turn-completed`   | 观察型 | 一整轮结束，含工具调用 —— **成功、失败或被中止都触发**                                       | 上述四个公共字段，加 `turnCount`（至今的用户文本消息数，含本轮）、`textMessageCount`（非空的用户 + 助手消息数）、`titleAutoGenerated`（标题仍出自自动化时为 `true`）、`recentText`（对话尾部，约 1000 字）                       |
| `permission.request`       | 判定型 | 一条安全策略要求判断某个操作（effect 为 `ask`），审批卡片即将弹出                            | 见下                                                                                                                                                                                                                     |

新增触发点是 ShuviX 的改动（触发点表加一行、业务处加一个 emit）；hook 自己发明不出来。

## `permission.request` —— 回答审批请求

只有 effect 为 `ask` 的规则会触发它。`force-ask` 规则的意思是「只由用户回答」，`deny` 直接拒绝，
`force-allow` 直接放行 —— 这些都不会交给 hook（内置策略一个都不用，你自己的策略可以用）。用户答过
「允许并记住」的路径根本不会询问：内置的路径规则把它排除在外。判定型 hook 派出的 agent 自己的询问直接
交给用户，所以审查员永远不会审查它自己。

载荷就是审查 agent 拿到的全部输入。它只装人写的东西和操作本身，从不装干活那个 agent 自己写的正文或
工具输出：

- `sessionId` —— 操作发生在哪条会话（运行派发在它之下）。
- `agent` —— 发起询问的 agent 的 `profile`（agent 名）与 `kind`（`root` / `spawned`）。
- `operation` —— `tool`（带它的动作，如 `session: create-sub-session`）、`action`（`read` / `write` /
  `execute` / `navigate`）、`objectType`（`command` / `path` / `database` / `gitTool` / `url` /
  `invocation`）、`target`（命令、路径、SQL 或 URL，截断），以及 `facts`：命令有 `channel`、`host`
  （ssh）、`sandboxed`、`unconfinedReason`、`background`；路径有 `path`、`requestedPath`、`diff`（截断）
  与 `isNewFile`；数据库有 `connection`、`dbType`、`readonly`；url 有 `scheme`、`host`、`browser`；
  一律带 `workingDirectory` 与 `platform`。
- `policy` —— 提出询问的策略名 `names` 与它们合并后的 `prompt`。
- `userMessages` —— 人写的东西，旧在前：人发的消息、人对 agent 提问的回答、人在审批卡片上写的反馈
  （第一条加最近八条，逐条截断）。在子会话里，取的是它所属的顶层会话。
- `delegatedTasks` —— 仅子会话：父 agent 派给它的任务（只是声明，不是许可）；其它会话为空。
- `recentOperations` —— 本会话最近至多十次判定，每条 `{ target, outcome }`。

回答就是 `next` 工具的参数，按固定的 schema 校验：
`{ decision: allow | ask | deny, risk: low | medium | high | critical, summary, reason }`。

- `allow` —— 不弹卡片，直接执行。`deny` —— 拒绝，agent 读到 `reason`。`ask` —— 弹出卡片，附上审查员的
  `risk`、`summary` 与 `reason`。
- 多个命中的 hook 并行运行，最严格的回答胜出（`deny` > `ask` > `allow`）。
- 没有回答 —— 超时、被停止、运行失败、结果不合格，或没有 hook 命中 —— 就问用户。坏掉的回答永远不会
  变成放行。
- 同一会话连续被拒三次、或累计被拒二十次之后，这个会话的询问直接交给用户；用户回答一次询问，连续计数
  清零。
- 设置 → 通用 → 安全里的**自动审查审批请求**开关可以整个关掉这一步。

## `when` 过滤

CEL（Common Expression Language —— 与安全策略同一个引擎，但没有 `inDir` 那类策略函数）。它必须在下面
的上下文上求值为**布尔**：

- `event` —— 上面的载荷**加上** `trigger`（触发点 id；因此 `trigger` 是保留的载荷键）。嵌套字段用点号读：
  `event.operation.objectType == 'command'`、`event.operation.facts.unconfinedReason == 'escalated'`；
- `env` —— `{ host: 'desktop' | 'extension', platform: 'darwin' | 'win32' | 'linux' }`。

读取载荷里没有的字段是错误，而错误意味着**不命中**（外加一条警告）—— hook 绝不会误触发。可选字段
用 `has(event.field)` 守住。

## 运行时规则（宿主侧，不在文件里）

- 一次运行 = 在**发出事件的那条会话之下**派发一次点名的 agent —— 与 `agent` 工具同一条路，所以工具、
  询问、LLM 日志与子代理面板都落在那条会话上，每次工具调用都过同一套安全策略。模型与思考档位 = 会话
  当前的，除非 agent 文件的 `shuvix-model` / `shuvix-thinking` 另有声明；hook 自己从不选。**未知 agent /
  没有可用模型**：跳过并记日志（配置错误，不算失败的运行）。
- **观察型触发点**：这个 hook 在这条会话上的上一次还没跑完时，新的触发被跳过（`busy`）。超时 5 分钟，到点
  中止。agent 的回答被丢弃 —— 它要留下的任何东西都得经自己的工具去做（记进知识库、用 `session` 工具设
  标题……）。
- **判定型触发点**：不去重 —— 每次询问各是一次判定。超时 60 秒。回答只从 `next` 读取，agent 写的正文从不读。
- 运行在归属会话的子代理面板与主进程日志里可见（`hook "<name>" run=… start / ok / failed`、
  `skipped …: busy | unknown-agent | no-model`）。没有日志文件。
- 删除会话会中止它的 hook 运行；停止一次工具调用会中止它正在等的审查。

## 内置 hook 与覆盖

`auto-title` 在 `session.prompt-accepted when event.isDefaultTitle` 与 `session.turn-completed when
event.titleAutoGenerated && event.turnCount == 2 && event.textMessageCount >= 3` 上点名 `titler`
agent；titler 用 `session` 工具的 `set-title` 应用标题。

`auto-review` 在每一次 `permission.request` 上点名 `permission-reviewer` agent。这个 agent 没有工具、声明
`shuvix-thinking: low`（关掉思考时，有的模型不调 `next`、把判决写成正文），它的文件就是审查规则。只有 ShuviX 会派发它：`agent` 工具派不动它，也不能用它开
子会话。

同名的用户文件整个取代内置 hook：想关掉一个，一条带 `when: false` 绑定的覆盖就够了；只想审查一部分操作，
给 `auto-review` 加一个 `when`（如 `event.operation.objectType != 'command'`）。想改变判断的方式，覆盖的是
agent：`~/.shuvix/agents/permission-reviewer.md`。agent 写 `~/.shuvix/hooks`、`agents`、`policies`、`skills`
是一次要询问的普通写入（ask-on-external-path —— 它们都不是可写的会话目录）：审查员被要求拒绝改写 ShuviX
自己的防护，沙箱里的命令也根本写不了那里。
想让每次这样的写入都摆到用户面前，就写一份针对 `vars.shuvixConfigDirs` 的 `force-ask` 策略（见
`policy-md`）。同名副本按 `shuvix-files` 条目里的规则处理。

## 刻意没有的

没有脚本块、没有编排原语、文件里没有结果 schema（判定型触发点自带一份）、没有提示词模板、没有并发或
超时键、没有日志文件。观察型 hook 拦不住任何事，判定型 hook 只出现在 ShuviX 本来就要停下来询问的地方。
如果一件事需要*改变*会话接下来做什么，它就不是 hook —— 它属于 agent 自己的提示词，或一条安全策略。
